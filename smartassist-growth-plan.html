Why this plan exists

SmartAssist already has strong internal proof, but weak cross-user visibility.

The right move is not to bolt on a giant analytics stack. The right move is to separate what the repo already proves from what only aggregated adoption data can answer.

What already exists

Product evidence is already in the codebase

  • smartassist analyze reads usage_log.jsonl and exposes hit rate, latency, and query behavior.
  • rag_dashboard surfaces reliability, corpus stats, and feedback counts.
  • smartassist dashboard turns runtime state into an operator-facing HTML view.
  • The QA harness, smoke scripts, and CI workflows already prove setup and runtime behavior repeatedly.
  • Website, PyPI publish, and npm release workflows already exist as distribution surfaces.
What is still unknown

Maintainer questions local logs cannot answer

  • How many external developers finish setup successfully?
  • Which agent integrations convert best?
  • Where do new users drop off in onboarding?
  • Which features drive repeated usage across many installs?
  • What churn signals appear across versions and operating systems?
✦
The plan works because it does not pretend these are the same problem. Local product health is already measurable. Cross-install adoption is not. The strategy wins by treating those as two different layers instead of mixing them into one fuzzy dashboard.

Shared KPI pipeline

How SmartAssist will collect useful KPIs across developers without breaking trust.

The maintainer KPI layer should be separate from the current local analytics layer. That means no uploading usage_log.jsonl, no prompt capture, and no raw project context. Shared KPIs come from anonymous lifecycle events and weekly rollups.

What stays local

Current project logs remain on the user's machine

  • mcp_server.py already writes local runtime evidence to usage_log.jsonl.
  • codex_activity.py appends local session metadata for the dashboard experience.
  • analyze_usage.py and generate_dashboard.py are already excellent for one project or one developer.
  • Those files are inputs for rollups, not the thing we should upload.
What gets shared

Only anonymous lifecycle events and weekly KPI summaries

  • install_started, setup_completed, setup_failed
  • project_initialized, agent_configured, doctor_ready
  • seed_completed, dashboard_opened, uninstall_requested
  • Weekly rollups: searches, searches with results, positive feedback, negative feedback, and weak categories
Implementation flow

Four stages make the KPI system safe and useful

1
Consent + anonymous install id Ask during setup or setup-agent, then store consent outside project workspaces.
2
Emit lifecycle events from existing CLI paths Setup, init, doctor, seed, uninstall, and agent configuration are the cleanest KPI anchors.
3
Build weekly rollups locally Summarize search counts, success rate, feedback ratio, and weak categories from existing local analytics.
4
Batch upload or export Flush a sanitized queue to a simple hosted collector, or generate an export bundle when hosted telemetry is not ready yet.

Where KPIs live

We should view KPIs in separate surfaces for local debugging, maintainer decisions, and release control.

If everything lands in one dashboard, it becomes noisy. SmartAssist needs one local operator view and one shared maintainer view, plus a weekly and release rhythm for decisions.

Existing local view

Project dashboard and local analytics

Developers should continue using smartassist dashboard, smartassist analyze, and rag_dashboard to inspect one project or one workspace at a time.

This is for troubleshooting onboarding, retrieval quality, and weak categories locally. It is not the main surface for cross-developer product decisions.

New primary surface

Maintainer aggregate dashboard

The shared KPI rollups should feed one maintainer-facing dashboard. The simplest version is a generated HTML page backed by the telemetry collector.

This view should filter by time, SmartAssist version, agent, and OS family, and it is the main place to watch setup conversion, ready rate, search success, retention, churn, and weak-category trends.

Decision ritual

Weekly scorecard report

The aggregate dashboard should generate one weekly scorecard summary with KPI deltas, top failures, biggest wins, and the next product decision.

Dashboards are for exploration. The weekly scorecard is what forces an informed decision.

Release gate

Version comparison view

Before each release, maintainers should compare the current version against the previous stable release on setup conversion, doctor-ready rate, search success, negative feedback, and uninstall signals.

This is how SmartAssist uses product evidence to decide whether to ship, hold, or rollback.

Decision cadence

How maintainers use the KPI surfaces

D
Daily or ad hoc Use the local dashboard and aggregate dashboard to inspect onboarding problems, product regressions, and usage anomalies.
W
Weekly Review the scorecard and choose the next product, onboarding, or growth priority from the KPI deltas.
R
Per release Check the version comparison view before publishing and again after rollout to catch regressions quickly.
Setup architecture

How to stand up the aggregate dashboard

1
Client telemetry helper Write opt-in lifecycle events to a user-level queue and build daily and weekly KPI rollups locally.
2
Collector API Accept anonymous events and rollups over one small HTTPS ingestion endpoint.
3
Shared KPI store Keep raw events, daily rollups, weekly rollups, and release rollups in one relational database.
4
Dashboard generator Produce a maintainer-facing HTML dashboard from rollup tables and publish it to a private URL.
Read model

What the dashboard should read from

W
Weekly rollups first This is the main KPI surface for strategic trends and informed decisions.
D
Daily rollups second Use these to spot regressions, onboarding failures, and recovery after fixes.
R
Release rollups third Compare the current version against the previous stable release before shipping.
!
Raw events only for drill-down Do not drive decisions from noisy client events when a stable rollup already answers the question.

Scaling path

Yes — this can scale without redesigning the client side

1
Phase 1 Local batching, one stateless collector, one relational DB, scheduled rollups, and a generated HTML dashboard.
2
Phase 2 Add a message queue and async workers if direct writes begin to compete with rollups or dashboard reads.
3
Phase 3 Move large raw history to cold or append-only analytics storage while keeping fast KPI rollups in the serving database.
Why it scales

The contracts stay stable while the backend evolves

C
Client contract The client keeps sending the same small anonymous event and rollup payloads.
D
Dashboard contract The dashboard keeps reading precomputed rollups, not raw event firehoses.
T
Upgrade triggers Only scale up when ingest latency, rollup windows, dashboard speed, or query responsiveness start to degrade.
Feedback system

Three feedback lanes, each with a different job.

SmartAssist already learns best from contextual product feedback. The growth plan keeps that core loop, then adds public and campaign feedback only where they improve adoption and roadmap clarity.

Lane 1 · product quality

In-product feedback

This is the highest-signal loop because it comes directly from real usage during real coding work.

  • :) and :( with context
  • rag_feedback
  • apply_feedback_protocol
  • Lesson creation, boosting, demotion, and comparison logging
Lane 2 · operator insight

Public feedback

GitHub should become the structured channel for setup blockers, success reports, use cases, and feature requests.

  • Issues for bugs and broken setup
  • Discussions for wins, blockers, workflows, and requests
  • Release threads for version-specific regressions
Lane 3 · growth learning

Campaign feedback

Every public launch should ask for the same next step so replies stay actionable and comparable.

  • Install it
  • Run setup
  • Use it for one real task
  • Report what worked, what broke, and which agent you used
↺
Why this loop should work It asks users for evidence, not opinions. That keeps the feedback system close to the product's real value instead of drifting into vague feature wishlist noise.

Why it will work

This plan compounds because each step is built on something SmartAssist already knows how to do.

The strategy is credible because it stays close to the repo's current strengths, current assets, and current audience instead of assuming a different product than the one that exists.

1. It starts from real product truth

SmartAssist already has usage analytics, reliability scoring, dashboards, smoke checks, and QA demos. That means the first measurement layer is not speculative.

2. It avoids trust-breaking telemetry

The plan keeps local-first as the default and adds one separate sanitized KPI layer. Raw project logs stay local, while shared telemetry is reduced to anonymous lifecycle events and rollups.

3. It targets a warm market first

Developers already using Claude Code, Codex, and similar tools feel the exact pain SmartAssist solves: repeated mistakes, weak continuity, and poor feedback retention.

4. It turns proof into distribution

README, overview docs, QA demos, and release notes become growth assets. The product does not need invented marketing theater; it needs its best evidence packaged clearly.
