01 / Overview
What This Feature Does
Turn emoticons into lasting project knowledge

When a user types :) or :( (optionally with context like :( dont do this to the theme), Claude becomes the intelligent curator of the knowledge base:

1. Per-Lesson Decisions (V2)

Claude sees a table of recently injected lessons with IDs, scores, and confidence levels. For each lesson, Claude decides: boost_lesson, demote_lesson, merge_lessons, or skip. No more blind reinforcement.

Intelligent Per-Lesson

2. Create / Merge / Retire

Claude can create_lesson (dual-path: curated + vectorized), merge_lessons to consolidate overlaps, or auto-retire lessons that were never helpful. Corpus capped at 300 lessons.

LLM-Powered Lifecycle-Managed

03 / Lifecycle
Lesson Lifecycle Management
Create, boost, demote, merge, retire — bounded corpus

How Lessons Get Removed

TriggerWhenWhat Happens
Auto-retiredemote_lesson drops boost to 0.0 AND ups == 0Lesson was never helpful. Removed from curated, marked retired in scores.
Mergemerge_lessons called by ClaudeSource lessons physically removed from curated. New consolidated lesson added. Sources marked superseded.
Manual blockUser runs xN in monitorSets blocked=True, removes from curated.

Corpus Capacity

Soft Cap: 300 Lessons

When curated_lessons.json reaches 300 entries, _add_to_curated() returns an actionable error: "Corpus at capacity (300). Merge or demote lessons first."

Dashboard shows: Corpus: 87/300 lessons (29% capacity)

Merges reduce count (removes 2+ originals, adds 1). Auto-retire reduces count too.

Feedback Log Rotation

Trigger: >10,000 Lines

During smartassist maintenance, if feedback_log.jsonl exceeds 10K lines:

  • Archive oldest lines to .bak file
  • Keep most recent 5,000 lines
  • Reset vectorization counter to match

Score Entry Lifecycle

Audit Trail

Score entries in lesson_scores.json are never deleted. Even retired/blocked entries stay (~100 bytes each). They serve as:

  • Audit trail for why a lesson was removed
  • Prevention of re-creating retired lessons
  • Historical feedback data (ups, downs, boost history)

04 / Quality Gates
6 Gates Protect the Knowledge Base
Only high-value, project-specific lessons get stored

The create_lesson MCP tool validates every lesson before storing it. If a gate fails, it returns an error message so Claude can retry with better input.

Example: Valid Lesson

✓
Gate 1 — Category: "code_edit" is in {testing, code_edit, git, architecture, pr_review, security, debugging}
✓
Gate 2 — Sentiment: "positive" is valid
✓
Gate 3 — Intensity: 4 is within [1, 5]
✓
Gate 4 — Length: "Always use semantic colors from theme instead of hardcoded hex values" = 69 chars ≥ 30
✓
Gate 5 — No Generic Start: Does not start with "good job", "be careful", etc.
✓
Gate 6 — Action Verb: Contains "use" — an imperative action verb

Example: Rejected Lessons

✗
"Use theme colors" — Too short (16 chars < 30)
✗
"Good job using semantic colors from the theme" — Starts with generic "good job"
✗
"Semantic colors are better than hardcoded hex values" — No action verb (descriptive, not imperative)
✗
"Remember to run tests before committing" — Starts with generic "remember to"

Action Verbs Accepted

use never always avoid prefer check run ensure include test verify add remove replace apply call import export wrap split move keep delete update follow mock assert validate configure set create

Storage Format

Entries are written to feedback_log.jsonl with the correction field populated (≥30 chars) to ensure vectorize_learnings.py picks them up:

{
  "timestamp": 1709500000.0,
  "signal": "thumbs_up",       // or "correction" for negative
  "category": "code_edit",
  "intensity": 4,
  "query": "",
  "response": "",
  "correction": "Always use semantic colors from theme instead of hardcoded hex values",
  "context": "Was styling login button component"
}

06 / Critical Review
Honest Assessment
Problems found, mitigations applied, and remaining risks

Issues Found & Fixed

1. Quality gate ordering bug (FIXED)

The "generic start" check was running after the "action verb" check. Lessons like "Good job using semantic colors" were rejected with "no action verb" instead of the correct "generic phrase" error. Claude would then add an action verb but keep the generic start, creating an infinite retry loop.

Fix: Moved generic start check before action verb check.

2. Redundant detection logic (FIXED)

detect_feedback_signal() had a duplicate branch that could never trigger. Simplified to a single FEEDBACK_SIGNALS.get(stripped) call.

3. Thompson deduplication for reinforcement (FIXED)

If 3 injected lessons were all category "testing", Thompson would get 3x the intended update. Added categories_updated set to ensure each category is only updated once per feedback signal.

Risks That Remain

Risk 1: Claude Might Not Call the Tool

The system relies on Claude choosing to call create_lesson after receiving instructions. Claude could hallucinate a response, acknowledge without calling the tool, or produce a low-quality lesson that passes quality gates but isn't useful. There's no enforcement mechanism — only "MUST" in the prompt.

Mitigation: Strong instruction wording + quality gates catch most junk. Could add a follow-up check in a future hook.

Medium Risk Prompt-dependent

Risk 2: Stale Last Injection

last_injection.json stores the most recently injected lessons, but it could be from a different conversation or hours ago. A :) typed in a new session would reinforce lessons from the previous session's last RAG injection.

Mitigation: Could add a timestamp to last_injection.json and ignore entries older than N minutes. Not implemented yet.

Medium Risk Cross-session

Risk 3: Action Verb Check is Word-Boundary Naive

The verb check uses " verb " in " lesson " padding, which works for whole words but misses verb forms like "testing" (not "test"), "avoided" (not "avoid"), or verbs at the end of a sentence without trailing space (handled by start-of-string check only).

Mitigation: The current verb list is large enough (31 verbs) that most imperative lessons will match. Could use regex word boundaries \bverb\b for more precision.

Low Risk Cosmetic

Risk 4: No Rate Limiting

A user spamming :) 50 times would create 50 lessons and boost scores 50 times. The boost is capped at 3.0x, but 50 feedback_log entries and 50 vectorization subprocesses could be wasteful.

Mitigation: Could add a cooldown (e.g., ignore duplicate signals within 30 seconds). Not critical since this is a developer tool, not a public API.

Low Risk Edge case

What Could Be Better

V2 Resolved: Blind reinforcement eliminated. V1 boosted/demoted ALL injected lessons equally. V2 gives Claude per-lesson tools (boost_lesson, demote_lesson) so only relevant lessons are affected.
V2 Resolved: Unbounded corpus growth. Soft cap at 300 lessons with merge_lessons to consolidate and auto-retire to remove never-helpful lessons. Dashboard shows capacity.
V2 Resolved: Signal+context support. :( dont do this to the theme now works. Context is passed to Claude for targeted feedback decisions.
Known limitation: Race conditions. Single-user dev tool. Concurrent sessions doing feedback at the same millisecond could cause last-writer-wins on lesson_scores.json and curated_lessons.json. Not worth file locking complexity for the use case.
