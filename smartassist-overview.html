How does retrieval work under the hood?

There are two retrieval paths that work in parallel. The hook uses fast lesson-only keyword search on every prompt. The MCP tool searches the broader SQLite projection on demand.

Path A: Hook keyword search (runs every prompt)

1

Tokenize the user's prompt

"style the header with a blue background" → ["style", "header", "blue", "background"]. Stop words ("the", "with", "a") are removed.

2

Expand synonyms

"style" expands to {"styles","styling","color","colors","theme"}. "color" expands to {"theme","hex","style"}. The expanded set now overlaps with L042's text.

3

IDF scoring against active lessons in smartassist.db

Each active lesson is scored by how many expanded tokens match, weighted by inverse document frequency (rare terms score higher). Lessons with boost from positive feedback rank higher. Blocked or retired lessons are skipped entirely.

4

Session dedup + inject

Lessons already injected in this session are skipped (tracked via rag_session_state.json). Top-5 results are formatted as [ID] [category] lesson text and injected as additionalContext in the hook output. Claude sees them before responding.

Path B: MCP rag_search (Claude calls on-demand)

1

Tokenize + expand query

"how to style components" becomes searchable tokens like {"style","components","theme","color"} using the same synonym expansion family as the hook path.

2

Search canonical projection

rag_search reads the SQLite search_documents projection, which contains active lessons plus vetted event memory. Category filters apply here, not against a separate store.

3

Apply boosts + format results

Lesson boosts, source-type weighting, and category filters are applied from the canonical store. Results are returned in the same lesson-focused format Claude already expects.

Why two paths? The hook path is lesson-only and optimized for every prompt. The MCP path searches the broader SQLite projection, so Claude can retrieve vetted event memory and active lessons on demand from the same canonical store. LanceDB is refreshed in the background as a cache, not a second source of truth.

5

Next session — Claude uses theme.colors.primary instead of #0000FF

// Guided by the LLM-created lesson: backgroundColor: theme.colors.primary // Instead of: backgroundColor: '#0000FF'

No repeated correction needed. The lesson — written by the LLM with full context — fires on every future styling-related prompt. It's specific enough to mention theme.colors and JSX style props, not just "use the theme."

How Lessons Get Injected & Improve Over Time

SmartAssist uses Thompson Sampling (a multi-armed bandit algorithm) and a MemAlign-style dual-memory pattern to continuously improve which lessons get injected. Semantic memory stores durable project rules. Episodic memory stores concrete past corrections. Every feedback signal makes retrieval and ranking sharper over time.

The RLHF Reinforcement Loop

This is the core learning cycle that makes the RAG database improve with every interaction:

1Retrieve: Keyword search finds 20 candidate lessons matching the user's prompt
2Thompson Rerank: Each candidate is scored by sampling from Beta(alpha, beta) — proven lessons rank higher (exploitation), new/untested lessons get fair chances (exploration)
3Inject: Top 5 results injected as dual-memory context — rules (lessons) + past corrections (episodes)
4Record: Injection tracked in lesson_thompson table (which lessons were shown, when)
5Feedback: User gives :) or :( → fractional credit attributed to injected lessons (weighted by relevance + recency)
6Learn: alpha += credit for :), beta += credit for :( → next retrieval is better

Result: Good lessons climb (high alpha → sampled higher). Bad lessons sink (high beta → sampled lower). New lessons get fair exploration (Beta(1,1) = uniform). Stale lessons gradually re-enter exploration (30-day decay). The system never stops learning.

Automatic: Hook Injection

Fires on every single prompt. Injects dual-memory context: project rules (semantic memory) + past corrections (episodic memory).

1Tokenize prompt, expand synonyms
2IDF keyword match → 20 candidates from smartassist.db

4Retrieve matching episodes (past corrections) from feedback events
5Inject: "Project rules: [lessons]" + "Past corrections: [episodes]"

MemAlign-Style Memory in SmartAssist

Inspired by Databricks' MemAlign framework, SmartAssist keeps two memory types and combines them into working memory at prompt time:

Semantic Memory (Rules)

Active lessons and conventions — durable project rules distilled from feedback or seeded from real repo context. "Always use semantic color tokens from the theme"

Episodic Memory (Corrections)

Past feedback events — concrete corrections and edge cases pulled from real sessions. "Last time hardcoded styles broke theme switching"

We keep both because they solve different jobs: rules tell the agent what good looks like, while episodes remind it what failed before and why it mattered.

At runtime, SmartAssist builds working memory by injecting the most relevant rules alongside a few similar past corrections. That combination makes guidance more reusable than examples alone and more grounded than rules alone.

Multi-agent support: SmartAssist provides setup surfaces for Claude Code, Codex, Gemini, ChatGPT, Amp, and OpenCode. Claude Code has the strongest runtime validation today because it uses the full hook lifecycle. Other agents use the same MCP tools and RLHF loop — they call rag_search to retrieve memory and apply_feedback_protocol to persist new reusable guidance via AGENTS.md guidance, skills, or generated instruction files — but broader end-to-end validation is still lighter outside Claude.

Limitations & Design Decisions

Things to know before relying on SmartAssist in production. Each item explains what the limitation is, why it exists, and the planned path forward.

Before broad public sharing, these pieces still need to close

1Public package-registry install paths are not live yet. The supported install path today is still the repo install.
2Claude has the strongest runtime proof. The other agent integrations still need broader end-to-end smoke validation.
3SmartAssist still needs a clean external-machine / external-user install proof before claiming broad public readiness.
4First-run onboarding still needs a tighter time-to-first-value proof: install, doctor, one feedback signal, then visible retrieval.
Categories are organizational labels, not a retrieval mechanism

What this means

Categories (testing, code_edit, git, etc.) are metadata labels attached to lessons. They are used for display, optional filtering in rag_search, Thompson Sampling grouping, dashboard breakdowns, and they are included in the searchable projection so category terms can help retrieval.

Why it's designed this way

Retrieval should still work even if categorization is imperfect because lesson text carries most of the weight. But categories are useful signal: they improve filtering, reliability grouping, and keyword overlap when the user explicitly mentions a domain like testing or git.

Current behavior

The hook auto-infers categories using a 3-tier fallback: majority vote from recently-reinforced lessons, then keyword matching against the feedback text, then a default. The MCP create_lesson tool currently validates categories against a fixed set of 7 engineering-focused labels and rejects unknown values.

Planned: open categories

Remove the fixed category validation. Any string will be accepted as a category — "risk_management", "execution", "compliance", whatever fits the project. The 7 engineering categories remain as defaults for keyword inference, but Claude can create lessons with any category via the MCP tool. No config file needed.

Hook search is keyword-based — it won't catch every semantic match

What this means

The UserPromptSubmit hook uses tokenization + synonym expansion + TF-IDF scoring. It matches literal words and a hardcoded synonym map. If a user says "change the background hue" and the lesson says "Don't use hardcoded colors", the hook might miss it because "hue" isn't in the synonym map for "color".

Why it's designed this way

The hook runs on every single prompt. It must complete in <50ms with no ML model loading. Loading an embedding model would add 4+ seconds to every prompt. The keyword approach is fast, predictable, and catches most practical matches.

Mitigation

The MCP rag_search tool provides the broader-projection fallback. When Claude encounters a topic that might have project-specific rules, it can call rag_search which searches the canonical SQLite projection across both active lessons and vetted event memory. Together, the two paths cover both fast lesson-only matches and wider project memory retrieval.

Curated lesson corpus is capped at 300

What this means

add_to_curated() rejects new lessons when the active lesson slice in smartassist.db reaches 300 entries. The MCP tool returns an error asking the user to merge or demote existing lessons first.

Why it's designed this way

The hook loads the active lesson slice from smartassist.db on every prompt and scores every lesson against the query. At 300 lessons this stays comfortably under the 50ms budget. The cap also prevents lesson drift — a smaller, curated corpus with high-confidence lessons is more useful than a large corpus of noise.

Mitigation

Use merge_lessons to consolidate overlapping lessons. Use demote_lesson to retire low-value entries (auto-retired at boost 0.0 with no positive feedback). Run smartassist maintenance to compact stale data. The broader rag_search projection still includes vetted event memory, so historical feedback remains searchable even after active-corpus cleanup. LanceDB mirrors that projection as a cache.

First-run embedding model download (~400MB)

What this means

The first time smartassist vectorize runs or the background cache refresh executes, it downloads the bge-m3 sentence transformer model from Hugging Face (~400MB). rag_search itself is SQLite-backed and works without that download.

Why it's designed this way

Local embedding means no API calls, no tokens consumed, no latency to external services, and no data leaving the machine. Everything runs on-device. The model is only loaded by vectorization tools that rebuild the optional LanceDB cache — the hook and rag_search never load it.

Impact

The first cache rebuild in a fresh environment has a cold-start download. Prompt injection and rag_search are unaffected because they read the SQLite store directly. In air-gapped or restricted environments, pre-download the model, skip cache rebuilds, or set HF_TOKEN for authenticated access.

Default keyword maps and synonyms are engineering-focused

What this means

The hook's synonym map expands "test" → {"testing","mock","assertion"} and "git" → {"commit","branch","merge"}. The category keyword map recognizes "jest", "detox", "firebase". These are software engineering terms. A trading project's domain vocabulary ("sharpe", "drawdown", "slippage") won't have synonym expansions or category mappings out of the box.

What still works

The hook's keyword search still matches literal words in the lesson text — if the lesson says "check drawdown limits before sizing" and the user types "drawdown", it matches directly. No synonym expansion needed. The MCP projection search still works for any domain because it scores the actual lesson and event text, not just hardcoded engineering categories.

Non-engineering domains

SmartAssist's core loop (capture feedback → create lesson → surface on relevant prompts) is domain-agnostic. The lesson text and the canonical SQLite projection carry the domain knowledge. Categories and synonyms improve precision for engineering but the system works without them. For non-engineering use: let Claude create lessons via create_lesson with domain-specific categories, and rely on projection search for retrieval.

Lessons are scoped per-project — no cross-project sharing

What this means

Each project has its own .claude/smartassist/ directory with independent lessons, scores, and vector database. A lesson learned in project A (e.g. "always use semantic colors") is not available in project B unless the user runs smartassist seed with a shared CLAUDE.md or manually migrates lessons.

Why it's designed this way

Project-specific lessons are more precise than universal ones. "Use renderWithProviders()" is correct for a React Native project but meaningless in a Python API. Per-project scoping prevents cross-contamination and keeps the lesson corpus relevant.

Workaround

Universal lessons (e.g. commit format, code review standards) can be shared via a team CLAUDE.md file. Run smartassist seed in each project to import them. The smartassist migrate PATH command can copy data from one project's SmartAssist directory to another.
